# P5 Items Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Generic magic items ("+1 Armor", "any sword") get a base when added, every item shows a stat-block card, inventory rows can be changed and split, and armor, shields and weapons are added as separate rows with an "Equip now / Equip and attune / Just add it" choice. A separate group of tasks hands the variant data and the template-text fix to the private compendium importer.

**Architecture:** One resolver, `entryItem(entry, registry)`, turns an inventory entry (library item + chosen base + per-row change) into the `ItemData` that every sheet calculation reads, so derive, attacks, gates, spells, rests and the UI see "+1 Slate Mail" with AC 15 without knowing about variants. Variant recognition lives in `src/content/item-variant.ts` (pure); the stat-block card is a pure fact list (`src/content/item-view.ts`) drawn by one DOM function (`src/ui/item-card.ts`). The importer work is Python on another branch and never touches the plugin repo.

**Tech Stack:** TypeScript, Obsidian plugin API, Vitest + jsdom (`npm test`, `npm run typecheck`, `npm run build`); importer: Python 3 stdlib `unittest` in the dnd-compendium venv.

**Spec:** `docs/superpowers/specs/2026-10-19-play-surface-design.md` (section 6, plus "My calls": Importer and generic items, Items are per row, Existing stacks are left alone).

## Global Constraints

- Plain DOM via `h()`, never innerHTML; mount roots use `classList`, never `className`.
- Every feature at parity on desktop (hover), tablet and phone (tap), 44 px targets on touch; layout parity tests place each feature id once per layout (this plan adds no feature id; every UI test runs in a `for (const layout of LAYOUTS)` loop).
- Plugin button rules need `.fe-sheet button.x` specificity to beat Obsidian's `button:not(.clickable-icon)`.
- Fixtures are INVENTED: never book or SRD prose or published stat blocks (the code is mirrored to a public repo). The bundled SRD numbers already in `src/content/srd/items.json` are data, not fixtures; tests use invented items.
- Plain words for players who are not rules-savvy; nothing race/class/feat/item specific in code.
- Existing notes without the new fields behave exactly as today (no `row`, `base`, `change` and no `variant` means today's numbers and today's stacking of existing rows).
- Never write to library or item notes from the sheet; changes live on the inventory entry in the character note.
- Test first; all existing tests keep passing (about 1500). Where a test encodes behaviour this spec changes, the task names it.
- Commits: conventional prefix, one sentence on why, last line `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Importer group: code only on branch `worktree-dnd-compendium` of `/docker/homelab-config` (worktree `/docker/homelab-config/.claude/worktrees/dnd-compendium`), never in the plugin repo, never mirrored; the vault is re-imported only after the user says go.
